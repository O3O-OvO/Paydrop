# Paydrop 下一轮迭代建议

评审日期：2026-10-10（北京时间）。基线：本地 v1.2.1，提交 `feee521`。

本次只检查与编写方案，没有修改业务代码、用户设置或工作记录，没有发布新版本。下面的版本号是建议，不代表已安排或已发布。

## 结论

下一阶段应从“好看的计薪挂件”走向“可信、可纠错、低打扰的桌面工作记录工具”。保留小八、数字滚动和金币，但优先解决状态含义、忘打卡、记录恢复与桌面便利性，不建议把更多动画作为下一版主线。

## 已确认的问题

### P1：跨日加班缺少异常提醒与纠错

步骤 1 和步骤 3 的当前 Web 数据有一条归属 2026-10-05 的加班记录，评审时累计超过 108 小时。它可能来自测试，不能认定用户真实连续工作了这么久；但代码确实允许主动加班无限延续，`advanceRecords` 有意不自动结束加班。

现有规则本身并非错误：不能凭应用关闭或系统休眠就断言用户已下班。缺口是没有异常提示，也不能按真实离岗时间修正记录；现在结束只会以当前时刻收尾。

建议：可配置的连续记录提醒、恢复应用时的“确认仍在工作”、安全的结束时间补录、修改前后差异和撤销。默认只提醒，不擅自扣除睡眠、闲置时间。

依据：`src/work-log.js:13`、`src/work-log.js:45`、`src/main.js:169`。

### P1：标准秒薪与当前计薪速度混淆

步骤 1 的挂件显示“加班中”、收入为零，却仍显示约 ¥0.0038 / 秒。模型实际提供 `rate` 和 `accrualRate` 两个值，挂件使用前者；无薪加班、无薪休息期间，前者非零不表示收入正在增长。

建议：主行显示“当前计薪 ¥0 / 秒”，标准秒薪放到详情。若仍把标准秒薪放在挂件，必须明确标为“标准秒薪”；有薪加班展示实际倍率后的速度。不要为修正文案修改已经正确的计薪公式。

依据：`src/widget.js:230`、`src/work-log.js:91`。

### P2：加班状态与下班说明矛盾

步骤 2 的页面 DOM 同时出现“加班中”和“本班已下班”。倒计时为零只是计划下班时间已过，不代表实际记录已结束。

建议：普通工作显示下班倒计时；加班显示“已加班”及持续时间；休息显示当前休息状态。结束后才显示“本班已结束”。当前截图只展示页面首屏，倒计时说明的矛盾由本次 DOM 和源代码共同确认。

依据：`src/main.js:208`。

### P2：配置备份不是完整的数据备份

目前配置导出只包含设置；工作记录 CSV 只导出汇总，无法恢复原始分段和班次薪资快照。已有原子写入和单份上一版本备份值得保留，但不等于用户可迁移、可恢复的完整备份。

建议：区分“导出配置”和“备份全部数据”，后者包含 schemaVersion、设置、记录、快照与生成时间。恢复先验证、预览数量和冲突，再自动备份当前数据。首版先做替换恢复，不急于做高风险的跨设备合并。

依据：`src/main.js:318`、`src/main.js:184`、`electron/data-store.cjs:35`。

### 第一优先：让用户能解释每一个数字

- 挂件保留一个主要收入数字，但当前计薪速度与标准秒薪必须分开。
- 日薪、计划有薪时长、班次薪资快照、加班倍率能在同一处核对。
- 普通工作、计划有薪休息、计划无薪休息、临时休息、无薪加班、有薪加班、展示暂停分别定义显示规则。
- 修改设置时提示“当前班次仍使用打卡时的参数，下次班次生效”，不偷偷改历史。
- 时间回拨、异常长加班、休眠恢复只提示异常和建议，不自动伪造考勤。

### 第二优先：记录页成为实用工具

- 点开班次看到每段开始、结束、休息、加班和实际收入依据，不只显示总时长。
- 修正记录时显示修改前后工作时长、无薪时长和收入差异。
- 删除先进入回收站，撤销使用明确记录版本校验，不以整份旧数据覆盖其他窗口的新记录。
- 日期范围筛选、备注、补卡标识和每周趋势在纠错能力完成后增加。
- 优先做本地完整备份；云同步与账号体系暂缓。

### 第三优先：减少操作负担

- 工作台压缩装饰性顶部区域，把班次控制、收入和时间指标移到首屏。步骤 2 的当前首屏里，时间指标仍在视口下方。
- 设置按“薪资与作息 / 挂件外观 / 桌宠 / 数据与更新”拆分，先见业务参数，减少长抽屉滚动。
- 常用设置不必全部进入工作台，挂件可提供有焦点管理的小菜单。
- 休息快捷入口明确区分“本人临时休息”和“小八歇一会”，保留不同标签与图标。
- 增大缩小布局下的图标点击区域；补键盘与低透明度可读性检查，不用大量教程文字替代可理解的控件。

## 工程与发布改进

1. **把回归脚本纳入常规测试。** 当前 `npm test` 有 63 项测试并在本次全通过，发布 workflow 执行单元测试和打包；上一轮浏览器与原生验证脚本放在被忽略的 `output/playwright` 下，尚未作为可复用 CI 门禁。应把核心场景移到受版本控制的 `tests/e2e`，使用独立用户目录，不读取真实薪资数据。
2. **增加真实升级验收。** 用独立 Windows 测试账户验证旧安装版到新安装版的下载、退出安装、重启、记录与设置保留、断网恢复。单元测试与发布附件校验不能代替真实安装升级测试。
3. **补 Electron 边界。** 已有 sandbox、contextIsolation 和禁用 Node 集成；再限制外部导航、窗口打开和 IPC sender。`pet-window.cjs` 已有窗口归属检查，可沿用到数据和更新 IPC。还应设计与现有内联样式相容的 CSP，不能直接套入过严策略造成透明窗口失效。当前未验证可利用攻击，不将缺少防御声明成已经被攻击。
4. **升级决策更清晰。** 当前默认自动下载并在退出时安装；可增加“自动下载 / 手动检查”偏好、更新说明与下载状态，避免用户把退出理解成永远不会安装更新。
5. **签名与素材分发检查。** Windows 签名是公开分发的后续工程项；不要承诺签名后一定没有 SmartScreen。同时核对角色素材、原始图片、开源依赖的授权和署名条件，再决定长期公开分发策略。本次没有完成授权判断。
6. **做长期性能基线。** 记录静止、动画、隐藏、休眠恢复时的 CPU 和内存；数据改变时仅在窗口相关设置真的变化后调用尺寸与置顶 API。该方向是待测优化，不能据此声称已有性能故障。

安全依据：[Electron 官方安全建议](https://www.electronjs.org/docs/latest/tutorial/security/)。
更新依据：[electron-builder v26 更新说明](https://www.electron.build/v26/docs/features/auto-update/)。

## 范围与取舍

- 本次运行全量单元测试，63 项通过；只对当前 Web 页面进行只读界面检查，没有重跑原生升级、完整键盘流程或多设备视觉测试。
- 当前 Web 记录与已安装 Electron 的数据相互独立，本次观察不能证明安装版也有同一条异常记录。
- 不建议下一版增加账号、排行榜、广告、默认强提醒，或从系统闲置自动判断用户离岗。
- 最有价值的下一步是 v1.2.2 状态修正，随后 v1.3.0 记录纠错与完整备份；新增小八动作作为小范围补充，不与这些核心能力抢优先级。
